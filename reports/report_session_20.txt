## 3. D11 — 모델 객체 생성 자체가 실패하던 문제
================================================================================

  현재 transformers 버전이 openai/clip-vit-large-patch14의 image processor를 인식하지
  못한다. CLIPProcessor.from_pretrained이 텍스트·이미지 프로세서를 함께 만들기 때문에,
  텍스트만 쓰는 QueryBlock에서도 이 오류를 맞았다.

  QueryBlock  CLIPProcessor → CLIPTokenizer. 토큰화 결과 동일함을 대조 확인.
  ImageBlock  이미지 프로세서를 지연 생성(property)으로. 서빙은 미리 뽑아 둔 CLIP
              특징(B, 1024)만 넘기므로 이 경로를 아예 타지 않는다. 서빙 venv에 PIL이
              없다는 사실이 이제 이미지를 실제로 넘길 때만 드러난다.

  주의 — encode_content는 model.to(device) 이후에 불러야 한다. SentenceTransformer가
  생성 시 자체적으로 mps를 잡는 반면 MLP는 cpu에 남아서, .to()를 건너뛰면 device가
  갈린다. 서빙 경로(ModelManager.load_model)는 .to(self.device)를 부르므로 해당 없다.

## 5. D9 결정 — 검색은 백엔드가 한다 (B)
================================================================================

  두 길이 동시에 열려 있어 다음 작업을 정할 수 없는 상태였다.

    A  추천 서버가 검색까지 하고 아이템 리스트를 준다 (/recommend)
    B  쿼리 벡터만 주고 백엔드가 자기 벡터 DB에서 검색한다 (/search/vector)

  B로 정했다. /recommend는 **대조용으로 남긴다** — B의 고유한 실패 방식이 "검색은
  성공하는데 결과만 조용히 엉뚱함"인데, 같은 질의를 우리 쪽에 넣어 보면 체크포인트
  어긋남인지 백엔드의 거리 계산 설정 문제인지 그 자리에서 갈린다. 백엔드 검색이
  정상으로 확인되면 닫는다.

  [판단 근거로 남겨둘 것] B는 실시간 의존성을 없애 주지 않는다. 검색어를 벡터로 바꾸는
  것은 여전히 우리 모델이므로 추천 서버는 항상 떠 있어야 하고, 거기에 655MB 동기화와
  버전 어긋남 위험이 추가된다. 그럼에도 B를 고른 것은 백엔드가 검색 결과를 자기 데이터
  (저장 여부·인기·본 것 제외)와 섞을 수 있어야 하기 때문이다.

## 6. 전달 번들 (scripts/export_index_bundle.py)
================================================================================

  dist/bundle_20260831/ — 570MB, 파일 7개.

    {domain}_vectors.npy    float32 (N, 768), L2 정규화
    {domain}_items.parquet  id, title, domain, year, image, url + row, point_id
    manifest.json           model_version · 건수 · sha256 · 필드 채움률

  지키는 불변식 둘:
    (1) vectors[i] 와 items[i] 는 같은 아이템이다. 인덱스 meta.parquet의 순서를 그대로
        따르고 canonical CSV는 id로 조인만 한다. CSV를 다시 읽어 순서를 만들면 어긋난다.
    (2) manifest의 model_version은 API 응답과 같은 함수에서 나온다
        (checkpoint_version을 dependencies.py 모듈 수준으로 빼고 양쪽이 부른다).

  가드 셋:
    · 벡터가 L2 정규화 상태가 아니면 중단 (내적을 코사인으로 쓸 수 없다)
    · canonical 조인 성공률 99% 미만이면 중단 (year·url이 조용히 전부 비는 것을 막는다)
    · id 형식이 도메인 규칙에 안 맞으면 벡터와 함께 제거

  최종 수치
    movie  39,515건  year 99.2% / image 99.3% / url 100%
    music  39,682건  year 89.8% / image 92.4% / url 100%
    book  110,594건  year 91.7% / image 97.0% / url 93.1%

  검증 — 백엔드가 할 일을 그대로 흉내 냈다. /search/vector로 받은 쿼리 벡터로 번들
  벡터를 직접 내적 검색해 /recommend와 대조했고, 두 질의 모두 상위 5건이 순서와
  점수(소수 셋째 자리)까지 일치했다.

## 9. 한국어 검색이 동작하지 않는다 — 이번 세션 최대 발견
================================================================================

  프론트 검색창이 한국어를 받는데, 그동안 아무도 몰랐다. 판정 평가 1,600건이 **전부
  영어**였기 때문이다.

  실측 (같은 뜻의 한/영 쿼리 40쌍, 현재 서빙 모델)

    쿼리 벡터 코사인   한국어 0.058   ← 영어 등가 문장과 거의 직교
    상위10 겹침        40쌍 전부 0.0%
    검색 최고 점수     영어 0.659 / 한국어 0.509

  한국어 결과 점수가 0.455~0.509 좁은 구간에 몰리는 것은, 쿼리 벡터가 의미를 담지 못하고
  공간의 평균 근처에 떨어질 때 나오는 모양이다.

  원인은 토크나이저다. CLIP 텍스트 인코더는 영어 BPE라 "비 오는 오후의 조용한 시간"을
  ë¹/Ħ/ìĺ/¤ 같은 27개 바이트 조각으로 부순다(영어는 단어 그대로 10토큰). 학습 쿼리도
  콘텐츠도 전부 영어라 모델이 한글을 볼 기회 자체가 없었다.

  [임시 해결] src/api/translation.py — 한글이 들어오면 opus-mt-ko-en으로 번역한 뒤
  인코딩한다. 재학습 없이, 백엔드 변경 없이 들어간다.

    적용 후   상위10 겹침 0.0% → 29.0%   최고 점수 0.509 → 0.645 (영어 0.659)

  29%를 해석하려면 기준이 필요해서 함께 쟀다 — **같은 뜻을 다르게 쓴 영어 문장끼리도
  상위10이 평균 44%만 겹친다.** 표현이 조금만 달라도 결과가 꽤 바뀐다는 뜻이다.
  즉 0%는 의미가 전혀 전달되지 않은 상태이고, 29%는 패러프레이즈 수준(44%)에 못 미치나
  그 근처다.

  [한계] 은유적 표현에서 번역이 흔들린다. 스타일별 코사인이 atmosphere 0.848 /
  direct 0.857 / philosophical 0.783인데 poet만 0.632다. 짧은 단어도 취약하다 —
  "하늘"이 sky가 아니라 "Heaven"으로 번역된다.

  [설계] 번역 실패가 요청을 죽이지 않는다. 원문을 그대로 인코딩하고 넘어간다(품질이
  떨어질 뿐 검색은 된다). 모델은 첫 한국어 요청 때 올린다. 응답에 translated_query /
  translated_text로 실제 인코딩된 문장을 실어 보내, 결과가 이상할 때 번역 탓인지 검색
  탓인지 가를 수 있게 했다.

  [근본 해결] 쿼리·콘텐츠 인코더를 다국어 계열로 통일한다. 그러면 백로그 A2(인코더
  비대칭)도 같이 풀린다. 재학습이 필요하므로 다음 사이클에서 판단한다.
  **판단 재료가 하나 없다 — 한국어 판정 평가.** 다음 평가에는 ko를 넣어야 한다.

## 11. Qdrant 확정에 따른 번들 정비
================================================================================

  Qdrant의 point id는 부호 없는 정수 또는 UUID만 받는다. 우리 id는 문자열이다.

  [함정] row를 point id로 쓰면 안 된다. row는 도메인 안에서만 0부터 매겨져서, 한
  컬렉션에 세 도메인을 넣으면 **movie 39,515개 전부가 music·book과 충돌해 서로
  덮어쓴다**(실측). point_id 컬럼을 넣어 갈랐다 —
  movie 1,000,000,000~ / music 2,000,000,000~ / book 3,000,000,000~.

  세 값의 역할
    row       벡터 파일의 몇 번째 행인가 (적재할 때만 쓴다)
    point_id  벡터 DB 기본키 (인덱스를 다시 만들면 밀린다)
    id        원본 키. **오래 남는 것은 전부 이걸로 저장한다**

  [갱신 규약] 부분 갱신 금지. 재학습하면 아이템 19만 개의 벡터가 전부 바뀌므로 일부만
  갱신하면 새 모델과 옛 모델의 벡터가 섞여 순위가 무너진다. 무중단 교체는 별칭 전환으로
  한다(새 컬렉션 적재 → 건수·model_version 확인 → 별칭 이동 → 옛 컬렉션 삭제).

## 12. 백엔드 요청에 대한 미해결 쟁점 (9/1)
================================================================================

  백엔드가 (가) parquet 불필요 (나) vectors.npy를 GitHub으로 (다) 이미지는 원본 URL로
  직접 다운로드를 제안했다. 각각 문제가 있다.

  [가] **parquet을 빼면 벡터를 아이템에 연결할 수 없다.**
       .npy는 이름 없는 숫자 행렬이다. 원본 CSV로 대신하면 행 수부터 다르다
       (원본 40,109 / 우리 39,515 — 중복 593 + 깨진 행 1을 걸렀다).
       실측: CSV 순서로 붙이면 12,760번 행부터 밀려 **67.7%가 다른 작품**이 된다.
         행 12,760  CSV 기준 Weirdsville (2007)     실제 The Warlords
         행 12,761  CSV 기준 The Dog Problem (2006) 실제 Spiral
       오류는 나지 않는다. 사용자가 화면을 보기 전까지 아무도 모른다.

  [나] GitHub은 100MB 초과 파일을 거부한다. 우리 벡터는 324 / 116 / 116MB로 셋 다 넘는다.
       Git LFS는 무료 한도가 저장·전송 각 1GB라 재학습마다 초과한다.
       그리고 **저장소가 공개다**(api.github.com 200 확인). book의 43.7%가 Goodreads
       CC BY-NC 4.0이라 파생 임베딩의 공개 배포는 백로그 C2를 앞당겨 건드린다.
       또 커밋하면 히스토리가 재학습마다 583MB씩 영구히 불어난다 — 어제 indexes/를
       추적 해제한 이유와 같다. **GitHub Releases가 대안**(파일당 2GB, 히스토리 무관).

  [다] 원본 URL로 받으면 표지가 줄고 쓰레기가 섞인다.
       · 어제 받은 Deezer 표지 9,902장은 원본 데이터셋에 URL이 없다
         (music_canonical.csv의 img는 여전히 10,011건이 'no'). 92.4% → 67% 수준으로 회귀.
       · Amazon CDN은 없는 이미지에도 200을 주면서 플레이스홀더를 보낸다
         (43B 1×1 GIF, 2254B "이미지 없음"). scripts/validate_image_urls.py에 기록돼 있다.
       · BX URL 271,360건 실측에서 유효한 것은 55.2%뿐이었다.

  이 쟁점들은 결론 없이 보류됐다. 백엔드 연동은 **9/15까지 미루기로 했다.**

  git checkout main이 main에 있던 6월치 파일을 복원했고, 이어진 머지가 삭제를 적용하며
  디렉토리째 지웠다. beast에서 다시 받아 복구했다(돌던 서버는 메모리에 들고 있어 무중단).
  main에서는 이제 추적 대상이 아니라 재발하지 않는다.

  [주의] 8/18 서버는 터미널에서 직접 띄워 접근 로그가 남지 않았다. 그래서 백엔드가 어느
  엔드포인트를 쓰는지 알 수 없다. 오늘 재기동부터는 logs/serve_8000.log에 쌓인다.

  [주의] 추천 서버가 맥북에서 Tailscale로 떠 있다. 맥이 꺼지면 백엔드도 멈춘다.
  로드맵상 8월말 AI 서버 이전이 지났는데 아직 그대로다.

  [주의] 쿼리 벡터 경로가 셋이다(POST/GET /search/vector, POST /embeddings). 문서에
  POST /search/vector를 정본으로 적었으나, 백엔드가 무엇을 쓰는지 확인 전이라 코드는
  그대로 뒀다.
