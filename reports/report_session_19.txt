## 2. 원인 — 이미지 토큰 상한 (실측 확인)
================================================================================

  네 번 모두 동일한 예외였다.

    ValueError: The decoder prompt (length 4268) is longer than the maximum model
    length of 4096.

  서버에서 프로세서로 직접 측정한 결과:

    이미지 크기        총 입력 토큰      비고
    500x750             508
    896x1120          1,302           ≈ 픽셀/784
    1000x1500         1,966
    1650x1650         3,503           ← 표지 한 장이 컨텍스트를 거의 다 먹는다

  Qwen2.5-VL 프로세서 기본값은 size.longest_edge=12,845,056px = 시각 토큰 16,384개까지
  허용한다. 큰 표지 한 장이 max_model_len(4096)을 혼자 넘기고, vLLM은 그 요청 하나가
  add_request에서 던진 ValueError로 배치 512건과 프로세스를 함께 종료시킨다.

  즉 "한 건의 입력이 전체 실행을 죽이는" 구조가 진짜 문제였다.

## 5. 결정 A — 입력과 라벨의 근거 범위 정렬
================================================================================

  _build_content_text(학습 입력)와 build_synopsis(라벨 생성 입력)는 같은 로직의
  복제본인데 갈라져 있었다.

    (1) 커밋 4bcc809(7/15)이 _build_content_text에만 Director/Cast/Release Date를
        추가했다. 라벨을 만든 Qwen은 감독·배우를 본 적이 없다.
    (2) build_synopsis만 description을 600자로 절단한다. description_synth 실측
        평균 548자, 600자 초과가 movie 29.7% / music 17.6%로 그 꼬리는 입력에만 있었다.

  정렬의 축은 두 개이고 서로 반대가 아니다:
    - 근거 사실(어떤 작품 정보를 봤나)은 겹쳐야 한다  ← 위 두 건이 이걸 깨고 있었다
    - 표현 형태(어휘·문체)는 갈라져야 한다            ← 겹치면 어휘 매칭 지름길 = 진단 (D)

  선택지와 결정:
    A. 입력을 라벨 기준에 맞춘다 (600자 절단, 감독/배우/개봉일 제거)  ← 채택
       비용 0(content_text는 prepare_dataset 시점에 생성), 변수 추가 없음
    B. 라벨을 입력에 맞춘다 — 쿼리 전량 재생성 GPU 2~3시간, 이번 사이클이
       "개선안 3 + 라벨 규칙 변경" 두 변수가 되어 효과 분리 불가
    C. 방치 — 미스얼라인만큼 개선안 3의 측정값이 희석됨

  A를 고른 근거는 이번 사이클의 목적이 개선안 3의 **효과 크기 측정**이라는 점이다.
  검증: 3도메인 9,000행에서 두 함수 출력 완전 일치(불일치 0건). 커밋 a1edee5.
  메모리에도 저장: memory/project_content_label_alignment.md

## 7. QA 도구 (scripts/qa_synth_outputs.py) — 커밋 3e595d4
================================================================================

  설계 원칙은 모든 지표에 대조군을 붙이는 것이다. "중복률 3%"는 그 자체로 판단이 안 되고
  "원문은 1%인데 합성본은 3%"여야 한다. 세분성은 원문과, 라벨 오염은 폐기한 오염 캐시와
  비교한다. 임베딩 대신 어휘 기반(MinHash+LSH) — GPU를 학습에서 빼앗지 않기 위해서다.

  검사 항목: ① 커버리지(캐시↔CSV 양방향 + 중복 ID) ② ID 프리픽스·basis 층화
            ③ 세분성 붕괴 ④ COMMON_RULES 위반율 ⑤ 쿼리 커버리지 ⑥ 쿼리-입력 어휘 겹침

  [movie 시험 실행 결과]
    - 8/5 사고 흔적 없음: 캐시 잔존 0건, CSV 미반영 0건
    - 중복 ID: movie 593행(1.48%) / music 354행(0.88%) / book 0행
      → 같은 아이템이 배치 안에서 false negative가 된다 (개선안 2와 같은 축)
    - 세분성 붕괴 없음:
          지표            합성본    원문
          완전중복률       0.015   0.015
          근접중복률       0.002   0.001
          평균최대유사도    0.002   0.001
      합성본이 원문보다 뭉치지 않았다 = 설계 노트가 경고한 "세분성 함정"을 피했다.
    - 제목 고유 토큰 보존 92.9%
    - 소스 없는 층의 환각 관측:
        [38426] Costa Brava (1946)  원문 nan
        합성: "...the quiet desperation of its protagonist, who grapples with
               personal demons amidst the stark beauty of the Mediterranean sea..."
      포스터와 제목만으로 인물·갈등을 지어냈다. THIN_SOURCE_RULE 위반.
      → "서사주장률"을 층별 지표로 추가 (movie: poster 0.102 / meta_only 0.062 /
         overview+poster 0.222(소스 있으므로 정상))
    - 리뷰 인용 패턴 8.7% — 오탐 가능성 있음, 육안 확인 필요
    - 쿼리 커버리지 movie 85.8%, 입력어휘겹침 0.242(기준선)
    - DSV 유효율은 캐시에 통과분만 저장돼 항상 1.0 → sanity check로 강등,
      실질 지표는 쿼리 커버리지로 교체

  [결과] 실패가 모든 축에서 균일하다 — 특정 층 배제 편향이 아니다.

    특성 비교 (성공 34,925 vs 실패 5,184)      성공군    실패군   배율
      has_synth                                1.000    1.000   1.00
      synth_len                              548.263  551.237   1.01
      has_local_img                            0.993    0.995   1.00
      title_nonascii                           0.004    0.004   1.03
    층별 실패율: overview 13.4% / overview+poster 13.0% / poster 9.4% / meta_only 2.1%
    제목 비ASCII: ASCII만 12.9% / ~20% 13.2% / 20~50% 14.3%

  아이템 특성이 아니라 생성·검증 쪽 문제라는 뜻이다. 유력 가설:
    validate_dsv가 파트 **정확히 3개**를 요구한다. 모델이 4개를 뱉거나 번호를 붙이면
    전량 폐기된다. 사실이라면 파서를 관대하게 고쳐 GPU 재생성 없이 대부분 회수 가능.
  확인 방법: --probe N (실패 항목 재생성 후 원본 출력과 거절 사유 분류). GPU 필요.

## 14. 설계 질문에 대한 실측 답변 (8/7)
================================================================================

  Q1. "description 2~3문장이면 짧지 않은가? 예전엔 긴 줄거리를 넣었는데 모델 용량을
       못 쓰는 것 아닌가?"

    all-mpnet-base-v2 토크나이저로 movie 4,000건 측정:
      기존(원문 줄거리 전체)  평균 148토큰  최대 311  384초과 0.0%
      현재(합성 + 600자 절단) 평균 122토큰  최대 224  384초과 0.0%

    - "엄청 긴 줄거리"도 실제로는 평균 148토큰이었다. SBERT 한도(384~512)의 40%로
      잘린 적이 없다. 현재는 122토큰(-18%)이다. 용량 여유는 양쪽 다 크다.
    - 다만 길이가 품질을 올린다는 근거는 없다. SBERT는 토큰 평균 풀링이라 길수록
      mood 신호가 사건 나열에 희석된다. 이번 진단은 "길이 부족"이 아니라 "타입
      불일치 + mood 어휘 부재"였고, QA ③이 그 개선을 확인했다.
    - 실제 손실은 있다: 600자 절단으로 movie 30%가 꼬리를 잃었고 감독·배우를 뺐다
      (결정 A의 대가). 토큰 한도로 보면 절단선을 1,200자로 올려도 여유가 충분하므로,
      다음 사이클에서 라벨을 재생성할 때 함께 상향하는 것이 합리적이다.
    - description 자체를 4~6문장으로 늘리는 것은 별개 문제다. 고유 디테일은 늘지만
      환각 여지도 늘고 mood는 희석된다. 근거 없이 지금 바꾸면 변수만 늘어난다 →
      baseline 학습 결과를 보고 A/B로 판단한다.

  Q2. "쿼리 생성에도 같은 문제가 있지 않나?"

    길이 면에서는 아니다. 쿼리는 사용자 검색어를 흉내내는 라벨이라 짧은 것이 목적에
    맞고, 쿼리 인코더가 CLIP 텍스트 인코더라 77토큰이 물리적 상한이다.
    대신 다른 제약 셋이 있고 모두 작업 순서에 반영돼 있다:
      - 형식 경직: validate_dsv가 정확히 3조각 요구 → 13~15% 폐기 (15절 1·2단계)
      - 입력 절단: 쿼리 생성기도 description을 600자만 본다 (10단계에서 복구 검토)
      - 페르소나 3종 고정 + 학습 시 평균 풀링 → 라벨 다양성 제한 (개선안 2)

  Q3. "따옴표는 왜 문제인가?"

    측정: 감싼 따옴표만 벗긴 문장과 원본의 SBERT 코사인 = 평균 0.9744 (최소 0.9047).
    임베딩 영향은 사실상 없다. 남는 이유는 도메인 간 표면 형태 비대칭 하나뿐이다
    (music 25%가 감싸임, movie 0.3% / book 0.7%). 방향은 진단 (A)와 반대쪽이지만
    크기가 작으므로 우선순위를 낮췄다.

## 17. 학습·평가 실행 결과 (8/7 ~ 8/14)
================================================================================

  15절의 4~7단계를 실행했고, 그 과정에서 데이터가 아니라 **학습 구조**에 결함이 있음이
  드러났다. 시간 순으로 기록한다.

  [1] 첫 학습 (8/7) — batch 64, stage1 10 + stage2 15, patience 5
      Stage 1은 정상이었다. epoch 5가 최적(val 1.8945)이고 6에폭부터 과적합(train↓ val↑),
      patience 5 소진 후 best를 되불러왔다.
      Stage 2가 이상했다 — val loss가 0.000313 → 0.000310으로 15에폭 내내 평평했다.

      배치 크기는 요청받은 256이 OOM이라 64로 내렸다. 128도 29스텝째에 터졌는데,
      원인은 누수가 아니라 텍스트 길이 편차다(content_text 평균 128 / 최대 244토큰).
      mpnet이 어텐션 행렬(배치×헤드12×길이²)을 12개 층 모두 역전파용으로 보관하므로
      긴 텍스트가 몰린 배치에서 한계를 넘는다.

  [2] 평가가 3일간 멈춰 있었다 (8/7 18:04 ~ 8/10)
      [movie] Index build failed: Unable to find a usable engine; tried 'pyarrow',
      'fastparquet'. 서버 venv에 parquet 엔진이 없어 메타 파일만 저장에 실패했고,
      train.py가 인덱스 빌드를 try/except로 감싸 경고만 남기고 넘어갔다. eval은 임베딩과
      메타가 **둘 다** 있어야 인덱스를 등록하므로 0개를 로드해 torch.cat([])에서 죽었다.
      임베딩(GPU 3.5시간)은 무사해 pyarrow 설치 후 메타만 CPU로 재생성했다.

  [3] 평가 지표가 6월과 호환되지 않았다
      eval_lang.py의 score는 모델이 자기 임베딩으로 계산한 코사인 유사도다. 학습이 바뀌면
      공간 자체가 달라져 실행 간 절대값 비교가 불가능하다. 6월의 "poet 0.86"은 전혀 다른
      축 — 사람과 Claude가 매긴 관련성 등급(o=2/a=1/x=0)의 평균이었다.
      → scripts/judge_eval_relevance.py 작성. 6월과 신규를 **같은 LLM 판정기로 블라인드
        재채점**한다. 판정 근거는 원문 필드만 쓴다(합성 설명을 쓰면 신규 실행이 유리해진다).
        판정기 신뢰도는 6월 사람 라벨과의 일치율로 함께 보고한다.

  [4] 개선안 3만 적용한 결과 — poet이 오르지 않았다
      2026-06 avg 0.698 / poet 0.628
      08-13   avg 0.769 / poet 0.512

  [5] 근본원인 4 발견 — 검색에 쓰는 표현이 순위 목적함수를 본 적이 없다
      상세는 docs/design_poet_style_alignment.md 근본원인 4와 커밋 bb0e5e5 참조.
      요약: 인덱스에 저장되고 검색되는 것은 ContentBlock 출력 z_content인데, Stage 1의
      대조 손실 세 쌍에 z_content가 없다. 그 융합을 학습하는 유일한 곳인 Stage 2의 손실이
      후보가 아니라 768개 임베딩 "차원"에 대한 분포를 맞추고 있었다. L2 정규화된 768차원
      벡터는 성분이 ±1/√768≈0.036이라 softmax가 거의 균등해져 기울기가 소멸한다.
        무관한 두 벡터의 KL 0.00128 vs 실제 val loss 0.00031 (같은 자릿수)
        아이템 간 평균 코사인 0.352(랜덤 초기화) → 0.441(15에폭 후) — 거의 안 움직임

## 19. CLIP 동결 버그와 개선안 1 결과 (8/14)
================================================================================

  [1] 발견 — CLIP이 동결되어 있지 않았다
      개선안 1(QueryBlock에 LoRA 부착)을 구현한 뒤 catastrophic forgetting 위험을
      점검하다가 찾았다. 각 블록 생성자는 CLIP을 동결하는데("Freeze CLIP parameters")
      Stage 1 시작 시 트레이너가 그것을 되살려 놓고 있었다:

          if 'lora' in name or 'mlp' in name:   # CLIP 각 층의 mlp 서브모듈이 걸린다
              param.requires_grad = True

      CLIP 트랜스포머의 각 층에는 `mlp`라는 이름의 feed-forward 서브모듈이 있다.
      그래서 query_block.text_encoder...layers.N.mlp.fc1.weight 같은 이름이 매칭돼
      인코더 내부가 전부 열렸다:

          query_block  헤드 1,574,656 / LoRA 589,824 / 인코더 내부  56,669,184  ← 열림
          image_block  헤드 1,836,800 / LoRA       0 / 인코더 내부 201,449,472  ← 열림
          text_block   헤드 1,574,656 / LoRA 589,824 / 인코더 내부          0  ← 정상

      SBERT만 무사했던 이유는 내부 층 이름이 intermediate.dense/output.dense라
      'mlp'에 걸리지 않기 때문이다. 세 블록 중 하나만 설계대로였다.

      결과적으로 CLIP 사전학습 지식 258M이 19만 건·lr 1e-4로 full fine-tuning 되고
      있었다. 이는 LoRA를 쓰는 이유 자체를 무효화하며, 개선안 1("동결을 푼다")도
      의미가 없어진다 — 이미 열려 있었기 때문이다.

      수정: 헤드 MLP는 `<block>.mlp.`로 시작하고 인코더 내부는 `...encoder.layers.N.mlp.`
      처럼 중간 경로에 있으므로 앞 두 조각으로 판별한다. 261,921,536 → 5,575,936.
      재발 방지로 _log_trainable()을 넣어 학습 시작 시 블록별 학습 파라미터 수를 찍는다.
      (커밋 245575a)
